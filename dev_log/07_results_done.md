# Unit 07: Results presentation - Completion Context

## What Was Implemented

Animated single-panel replay and an upgraded comparison dashboard, built on top of Unit 06's existing UI: `RunState['done']` now retains each trial's full `TrialRunResult[]` (previously discarded once metrics were computed) plus a snapshotted `BuildingConfig`; a new `AppState.replay` selection tracks which algorithm/trial/time/speed is being watched. The replay cross-section shows a building grid (floor rows × elevator-shaft columns) with cars positioned via reconstructed-from-log interpolation, door state, passenger-count badges, and hall-call indicators, driven by a `requestAnimationFrame` loop that never touches the outer app's `render()`. The dashboard table is sortable and highlights the best algorithm per metric.

## Key Decisions

- Side-by-side multi-algorithm replay (watching the same trial across algorithms simultaneously, made correctness-free by Unit 04's fairness guarantee) is deferred as a fast-follow, not baseline — single-panel replay only.
- Dashboard ships table-only; no bar charts in this unit.
- Default playback speed options: 1x/5x/10x/20x, 5x default.
- `RunState['done']` retaining full per-trial event logs in memory (not just aggregated metrics) is a deliberate, accepted tradeoff at this project's scale.

## Deviations from Plan

**A real bug in the plan itself, found and corrected during review, before implementation started.** The original draft's position-interpolation algorithm would linearly interpolate an elevator's position across the *entire* span between two `elevatorArrived` log entries — but when a stop occurred at the earlier one, that span includes the dwell time (`doorsOpened` to `doorsClosed`), not just travel time. Naive interpolation across the whole span would show the elevator visibly creeping during what should be a motionless door-open period, then creeping too slowly once actually moving. Corrected: interpolation anchors to the `doorsClosed` timestamp (not the `elevatorArrived` timestamp) whenever a stop occurred at the earlier arrival. Implemented verbatim from the corrected pseudocode; a regression test explicitly computes and asserts against the exact numeric value (2.875) the original buggy algorithm would have produced, versus the correct value (2.5) at the same probe time — confirmed by independent code review to be a genuine differentiating test.

No deviations from the approved (corrected) plan during actual implementation. One incidental note: the implementing agent's session was interrupted by a rate limit right after finishing all code, tests, and browser verification, before writing up the final two dev-log sections (AI Interactions, Files Modified) — those were completed directly by the reviewing session afterward, after independently re-verifying the interpolation fix and the full test suite.

## Lessons Learned

The interpolation bug caught during this unit's plan review is the project's clearest example yet of a subtle log-reconstruction error that would have shipped as a "looks fine at a glance, wrong on close inspection" defect — the animation would have played smoothly and looked plausible; only a frame-by-frame check against the actual dwell timing would reveal the elevator moving during a period it should have been stationary. This continues a pattern going back to Unit 05: reconstructing state from an event log rather than reading it directly is exactly the kind of code that warrants tracing by hand against a concrete example before trusting it, regardless of how confident the surrounding prose sounds.

## Amendment (during Unit 09 review): idle elevators appeared to move before being recalled

Developer-reported, from watching an actual replay: an idle elevator parked at a floor could be seen "slowly moving down" well before it was ever actually dispatched. Traced live alongside an FCFS dispatch investigation (see `03_algorithms_done.md`'s concurrent-dispatch discussion): under a sustained backlog, an elevator can legitimately sit idle and unassigned for tens of seconds — correctly excluded from candidates only because nearer elevators keep winning the assignment first — before finally being recalled once every nearer car has taken its turn.

This unit's original interpolation fix (the "Correction" note above) only ever detected *one* kind of pause: a door-dwell starting exactly at the earlier `elevatorArrived` timestamp. It had no way to represent "stopped, doors closed, and then sat idle/unassigned for an arbitrary stretch before finally being recalled" — so it treated the entire gap after `doorsClosed` as one continuous interpolated move, visibly creeping the elevator toward its eventual next floor for the whole idle stretch, not just the real final `floorTravelTimeMs` of it.

Fixed by replacing door-event detection with a simpler, more general anchor: a floor-to-floor move always takes exactly `floorTravelTimeMs` (verified directly against a full simulation event log — every travel leg matches the configured constant, with or without a preceding stop), so motion toward the next arrival can never have started before `nextArrival.time - floorTravelTimeMs`. Everything before that instant — dwelling, idle, or both in sequence — now renders fixed at the earlier floor, regardless of *why* the elevator was paused. This also simplified `positionAtTime` itself, which no longer needs to inspect `doorsOpened`/`doorsClosed` at all (still used elsewhere, by `doorsOpenAtTime`). `groupReplayLog` now takes the building's `floorTravelTimeMs` as a parameter and carries it on `GroupedLog` for this purpose.

Two new regression tests added: one proving position stays fixed through both the dwell and a subsequent 44-second idle gap (the original bug would show it about 30% of the way to the next floor by that point), one proving interpolation correctly starts only in the real final `floorTravelTimeMs` window. All prior interpolation tests (the original "Correction" regression) still pass unchanged against the rewritten algorithm. 188/188 tests pass; lint/build re-verified clean. Not yet re-verified against a live browser replay (Chrome extension unavailable this session) — worth a visual pass before considering this fully closed.

## Amendment (during Unit 09 review): onboard count jumped instantly instead of ramping across a dwell

Developer-reported: watching 8 passengers board at once, the displayed onboard count jumped straight to 8 immediately, despite the doors staying open for several more seconds of dwell. Traced to `simulation.ts`'s `handleStop`: every passenger boarding (or alighting) at a single stop shares the exact same log timestamp (the stop's start) — `door.ts`'s dwell formula scales the *total* dwell duration by headcount but never stages individual boarding moments. `onboardCountAtTime` was accurately reflecting that data; it just looked wrong on screen.

Explicitly scoped with the developer to a **display-only** fix: the simulation's boarding model, event log, and every metric derived from it (including each passenger's `boardedAt`-based wait time) are untouched. Genuinely staggering boarding timestamps in the engine was considered and declined — it would change core simulation semantics and shift measured wait times, which is out of scope for what was reported as a display issue.

Fixed in `replayFrame.ts`: `onboardCountAtTime` now detects when `time` falls within an open-doors window and, if so, linearly ramps the displayed count from the value just before that stop's own boarding/alighting (found via a new `countStrictlyBefore` helper, excluding entries at the stop's own timestamp) to the final post-stop value, reaching the true count exactly at `doorsClosed` and rounding to the nearest integer along the way (so it still reads as discrete people, not fractional ones). Works symmetrically for a net decrease (alighting) as well as increase, and correctly resumes from whatever the real prior count was, not from 0.

Two new regression tests: one proving an 8-passenger boarding ramps 0→2→4→6→8 across an 800ms dwell, one proving a 3-passenger alighting ramps 8→7→6→5 across a 400ms dwell starting from the real prior count. All prior onboard-count tests (which have no door events, so never mid-dwell) pass unchanged. 190/190 tests pass; lint/build re-verified clean. Not yet re-verified against a live browser replay (Chrome extension unavailable this session).

## Amendment (post-Unit-10, at developer request): per-elevator status label in the replay

Developer-requested: show each elevator's status above it in the replay — floor X while traveling somewhere, idle, etc. The simulation's event log has no explicit "elevator became idle" or "started traveling" event to read this off directly (same gap `positionAtTime` already works around); added a new `statusAtTime` in `replayFrame.ts` that infers it from the same arrival/door log data, reusing `positionAtTime`'s own phase boundaries: `[a.time or dwellClose, travelStart)` is stationary (`doorsOpenAtTime` distinguishes dwelling-with-doors-open from idle-and-unassigned), `[travelStart, b.time)` is actively traveling toward `b.floor`.

New exported `ElevatorStatus` union (`idle` / `doorsOpen` / `traveling` with a `targetFloor`) on `ElevatorReplayFrame`. `replayCrossSection.ts` renders it as a small label ("Idle" / "Doors open" / "→ Floor N") above each elevator's shaft, with a fixed width and reserved two-line `min-height` so a status changing length (e.g. "Idle" → "→ Floor 12") never shifts the shaft or floor grid below it — the same layout-stability principle the developer asked for earlier for the waiting-count badges (see this file's own history and `09_waiting_counts_done.md`'s amendment), applied proactively here.

Five new regression tests walk one scenario through all four phases in sequence (idle before any arrival, doors open during a real stop, idle again after doors close but before real travel starts — the same "idle-then-recalled" case as the position fix above — traveling toward the next arrival's floor, idle again after the last arrival) and assert the exact status at each. Verified live via Playwright (Chrome extension still unavailable this session): played a real run, captured both "Idle" and "→ Floor N" rendering correctly and updating live during playback, positioned cleanly with no observed layout shift. 221/221 tests pass; lint/build re-verified clean.

### Follow-up fix (same session): target floor was the next pass-through floor, not the real destination

Developer-reported immediately after: "Floor N" changed on every single floor crossed rather than naming where the elevator was actually headed. Root cause: `targetFloor` was set to `b.floor` (the next `elevatorArrived` entry), but `elevatorArrived` fires for every floor passed through, stop or not — `b` is only ever the immediately adjacent floor, never the real destination, for any trip spanning more than one floor.

Fixed: `statusAtTime` now finds the floor of the next `doorsOpened` event at or after `time` (the next floor this elevator will actually stop and open its doors at, however many pass-through floors away), falling back to `b.floor` only when no further stop is recorded at all (e.g. a homing elevator's final approach to floor 0, which just arrives and goes idle without a real stop). Two new regression tests: one sweeping floor 4→5→6→7 with a real stop only at 7, proving the target reads 7 throughout the whole sweep rather than 5 then 6 then 7; one confirming the status switches to `doorsOpen` (not `traveling`) exactly on arrival at the real destination. 223/223 tests pass; lint/build re-verified clean. Re-verified live via Playwright: the target floor now holds steady across consecutive frames within one trip instead of incrementing every floor.

### Second follow-up fix (same session): the entire first leg of a trip showed idle instead of the destination

Developer-reported immediately after, phrased as "the destination should be the call floor, not the floor it is in": traced this (via a direct simulation-and-log trace, not guesswork) to a second, distinct bug in the same function. `statusAtTime`'s very first check, `if (arrivalIndex < 0) return { type: 'idle' }`, unconditionally treated "no `elevatorArrived` entry yet" as idle — but an elevator dispatched immediately at t=0 doesn't log its first arrival until a full `floorTravelTimeMs` later, so its entire first leg (however many floors away the call is) showed "Idle" the whole time, even though it was already committed and moving. Confirmed via three traced simulation runs (FCFS, SCAN/LOOK, and a multi-stop FCFS case) that the *destination floor itself* was always correct once travel was detected — the bug was specifically the detection of "is it already traveling" during this one window, not the target-floor computation fixed above.

Fixed by extending the same `travelStart`-anchored logic `positionAtTime` already uses for its own "starts at floor 0" convention: before the first arrival, `b` is `arrivals[0]` (the eventual first arrival) rather than automatically absent, so `travelStart = b.time - floorTravelTimeMs` is computed the same way as every other leg, and the elevator correctly shows `traveling` (toward its real destination, via the existing next-`doorsOpened` logic) once `time >= travelStart`, not just `idle` for the whole gap. Two new regression tests split the previous single "idle before first arrival" test into a genuinely-idle-before-dispatch window and an already-traveling-before-first-arrival window, against the same fixture. 224/224 tests pass; lint/build re-verified clean. Live re-verification of this specific edge case (a scenario where the very first dispatch target isn't the elevator's own starting floor) proved impractical this session — every readily available scenario configuration (default up-peak, the scripted demo) originates its first passenger at floor 0, the elevators' own start, so the first stop is always zero-distance and never exercises this code path; the fix is proven by the new deterministic unit test instead, which traces the exact reported scenario by hand.

### Third follow-up fix (same session): the new status header misaligned the floor grid

Developer-reported: with the status label now sitting above each shaft, the shafts no longer lined up with the "Floor N" rows beside them. Root cause: the status label added height above the shaft, but the floor-label column had no equivalent header content, so the floor-label column's rows started higher than the shaft's own floor-position grid — a pure CSS oversight, not a logic bug (`replayFrame.ts`, `positionAtTime`, and every test were unaffected).

Fixed in `replayCrossSection.ts`: introduced a `STATUS_HEIGHT_PX` (28px) constant, used both as the status label's fixed height (switched from a content-driven `minHeight`/`marginBottom` to a fixed height with flexbox vertical centering, so a two-line status like "→ Floor 12" no longer grows the box) and as an empty spacer's height prepended above the floor-label column's rows. No test changes needed (this is a DOM-rendering-only file with no automated tests, per this project's established split — see `dashboardCharts.ts`'s precedent). Verified via Playwright with an exact pixel measurement: the first floor row and the shaft now start at the identical `top` (404px in the verification run), with every subsequent row exactly `ROW_HEIGHT_PX` (40px) apart, confirming pixel-exact alignment rather than an eyeballed "looks close enough."
