# Unit 06: UI

## Objective

Deliver the config-panel/run UI named in `00_main.md`'s Planned Units list: a building/fleet/timing/arrival config panel (floors, elevators, capacity, floor-travel time, door-dwell base + multiplier, arrival rate, origin/destination pattern, per-floor rate, trial count), run controls, and algorithm selection for comparison — all in vanilla TS against the DOM, no framework (confirmed against `package.json`: no React/Vue/etc. in `dependencies` or `devDependencies`, only Vite/Vitest/ESLint/Prettier/TypeScript).

**Scope boundary vs. Unit 07 (resolved — see Open Question 1):** `00_main.md`'s Unit 06 bullet does not mention displaying results; that's explicitly Unit 07's job ("animated replay... plus a dashboard"). But a config-and-run UI that shows nothing meaningful afterward can't be verified as actually working by using it — and this project's units are consistently verified end-to-end (see `02_engine_done.md` through `05_metrics_done.md`'s amendment history: every prior unit's "run it for real" testing found a bug earlier units' narrower tests missed). This plan's resolution: Unit 06 includes a deliberately plain, unstyled results readout — enough to prove config → `runTrialBatch` → `computeMetrics` works end-to-end when clicked through in a real browser — but explicitly *not* the polished dashboard/replay Unit 07 will build. Flagged for developer sign-off since it's a real scope-boundary call, not picked silently.

This unit consumes, without modifying: `Scenario`/`RandomScenario`/`ScriptedScenario`/`ArrivalPattern`/`RandomArrivalParams` (`src/generation/types.ts`), `runTrialBatch` (`src/generation/trialRunner.ts`), `algorithms: Algorithm[]` (`src/algorithms/index.ts`), `computeMetrics`/`AlgorithmMetrics` (`src/metrics/index.ts`, `types.ts`), `BuildingConfig` (`src/engine/types.ts`), and `scenarios: Scenario[]` (`src/scenarios/index.ts`, the auto-discovered scripted examples). No changes to `src/engine/`, `src/algorithms/`, `src/generation/`, `src/metrics/`, or `src/scenarios/` are expected.

### State model (`types.ts`, `state.ts`)

A single mutable `AppState` object, held once inside `app.ts`'s `mount()` closure, plus one `render()` function that rebuilds the DOM from current state. This is the standard vanilla-TS pattern for a small app and deliberately not over-engineered (no pub/sub, no virtual DOM, no reactive framework):

```ts
interface AppState {
  config: ConfigDraft;      // everything the config panel edits
  selectedAlgorithmIds: string[];
  run: RunState;             // 'idle' | 'running' | { status: 'done', results } | { status: 'error', message }
}
```

**Practical refinement to plain "re-render everything on every change"**: a full-subtree `innerHTML` rebuild on every keystroke would destroy and recreate `<input>` elements, losing focus and cursor position while typing a number — a real usability problem, not a hypothetical one. Resolution: text/number inputs in the config panel are wired with direct `oninput` handlers that mutate the corresponding `AppState.config` field in place and do **not** call `render()` — the input already shows what the user typed; no re-render is needed for that field itself. `render()` (rebuilding a subsection's DOM) is called only when a change is *structural* — the set of visible fields changes shape, not just a value:
- floor count changing (changes the valid `floorRates` row set),
- arrival pattern changing (changes which floors are shown for per-floor-rate override — see below),
- scenario type toggling between random and scripted (shows/hides whole sections).

The algorithm checkboxes and the run-controls/results sections have no persistent-focus text inputs, so they're simply rebuilt wholesale on every relevant state change — no special-casing needed there.

### Config panel fields and defaults (`configPanel.ts`)

One field per `00_main.md` bullet, each with a sensible default so the page is immediately runnable without any input:

| Field | Maps to | Default |
|---|---|---|
| Floors (above ground) | `building.floorCount` | 5 |
| Elevators | `building.elevatorCount` | 2 |
| Capacity | `building.capacity` | 8 |
| Floor travel time (ms) | `building.floorTravelTimeMs` | 2000 |
| Door dwell base (ms) | `building.doorDwellBaseMs` | 3000 |
| Door dwell per-passenger multiplier | `building.doorDwellPerPassengerMultiplier` | 0.5 |
| Arrival rate (per minute) | `arrivals.baseRatePerMinute` | 6 |
| Origin/destination pattern | `arrivals.pattern` | `'up-peak'` |
| Per-floor rate override | `arrivals.floorRates` | none set (all floors inherit the base rate) |
| Trial count | `trialCount` | 10 |

"Floors (above ground)" is labeled explicitly as such, not just "Floors" — `BuildingConfig.floorCount` is floors *above* ground (valid indices `0..floorCount` inclusive, `floorCount + 1` levels total per `src/engine/types.ts`), and a bare "Floors: 5" label would be a natural off-by-one trap for a first-time user.

**`durationMs` and `seed`** (needed by `RandomScenario` but not named in `00_main.md`'s field list — resolved, see Open Question 3): both are exposed as editable fields with defaults, not hidden entirely — this is a teaching tool, and both control genuinely interesting behavior (duration = how much load accumulates; seed = exact reproducibility of "run it again").
- Duration: numeric input in minutes for readability, converted to `durationMs` internally. Default 5 minutes.
- Seed: numeric input, defaulting to a freshly random value generated once when the page loads (`Math.floor(Math.random() * 0xffffffff)`, `Math.random()` is fine here — it's only ever used to *pick* a seed, not inside the reproducible simulation itself), plus a small "Randomize" button next to it that redraws a new default. Editable directly so a user can pin a specific seed to reproduce a specific run.

**Per-floor rate override** (`arrivals.floorRates`): minimum-viable treatment consistent with "no premature abstraction" — rather than always listing every floor (most of which are irrelevant under most patterns) or building a generic dynamic-rows editor, render one optional numeric input per floor **that the currently-selected pattern actually generates arrivals from** (mirrors `randomArrivals.ts`'s own `generatingFloors(pattern, floorCount)`: `up-peak` → floor 0 only; `down-peak` → floors `1..floorCount`; `random` → all floors `0..floorCount`). Each input starts blank (inherits `baseRatePerMinute`); a filled-in value becomes that floor's `floorRates[floor]` entry, an empty one is simply omitted from the built `Scenario`. This list re-renders (structural change, per the state-model note above) whenever floor count or pattern changes. Showing only the relevant floors avoids a config panel where a user sets a rate on floor 3 under `up-peak` and it silently no-ops — the UI only ever offers overrides that can possibly matter, rather than needing separate validation to explain why one didn't.

`generatingFloors` itself is currently a private, unexported function in `src/generation/randomArrivals.ts`. Rather than duplicating that pattern-to-floors logic in the UI layer (a drift risk — if Unit 04's rules ever change, the UI's copy could silently disagree), this plan recommends exporting it from `src/generation/index.ts` as-is and importing it here. This is a small, additive, non-breaking change to an already-completed unit (the same kind of cross-unit touch-up `02_engine_done.md`'s amendment history establishes as normal practice for this project), not a redesign of Unit 04. Called out here rather than done silently since it does touch a previously "done" unit's file.

### Scenario type toggle: random vs. scripted (`configPanel.ts`)

A two-option selector at the top of the config panel: "Random" (default) vs. "Load example scenario." Resolved in favor of including this (see Open Question 2) — `src/scenarios/` (Unit 04) exists specifically to hold reproducible, hand-authored teaching examples (`upPeakDemo.ts` today, auto-discovered via `src/scenarios/index.ts`'s `import.meta.glob`, exactly mirroring the algorithm-discovery mechanism this UI already depends on), and a UI that never surfaces them leaves a working, purpose-built Unit 04 feature dead and unreachable.

- **Random** mode shows the full building/fleet/timing/arrival panel above, and `buildScenario` constructs a `RandomScenario`.
- **Scripted** mode shows a dropdown of `scenarios` (from `src/scenarios`, labeled by filename/id since `ScriptedScenario` carries no display name field today — a small gap, not worth a cross-unit change for one label). Selecting one displays its `building` config **read-only** (informational — a `ScriptedScenario`'s building and script are fixed by construction) and hides the random-arrival fields (pattern, rate, per-floor rates, duration, seed — none apply). Trial count remains editable (Unit 04 explicitly kept `trialCount > 1` legal for a scripted scenario — N identical trials — per `04_generation_done.md`'s "Key Decisions"). `buildScenario` in this mode returns the selected `ScriptedScenario` directly (with the UI's current trial count spliced in, since the stored scenario's own `trialCount` is just its own default).

### Algorithm selection (`algorithmSelect.ts`)

A checkbox per entry in `algorithms` (`src/algorithms`'s auto-discovered list — no hardcoded algorithm names, so a future fourth algorithm shows up here automatically), labeled by `algorithm.name`, all checked by default. `AppState.selectedAlgorithmIds` tracks the checked set. No "select all/none" convenience control — three items doesn't warrant it; can be added later if the algorithm count grows.

### Run controls and the minimal results readout (`runControls.ts`, `resultsView.ts`)

A single "Run" button. On click:

1. `validate(state)` — thin pre-run guard (see "Validation" below); if it fails, show the message inline and stop, without touching `AppState.run`.
2. Set `state.run = { status: 'running' }`, call `render()`, then defer the actual work one tick (`setTimeout(fn, 0)`) before starting it — `runTrialBatch` is synchronous and can be CPU-heavy (many trials × long duration), and without this deferral the "Running…" state would never actually paint before the main thread blocks. This is the one place in the app where the state-then-render order matters for a reason beyond simple correctness.
3. `buildScenario(state.config)` → `runTrialBatch(scenario, selectedAlgorithms)` → `computeMetrics(trialResults, scenario)`, wrapped in `try/catch`.
4. On success: `state.run = { status: 'done', metrics: AlgorithmMetrics[] }`. On thrown error (e.g. the engine's own `doorDwellBaseMs > 0` validation, or a generation-layer negative-rate rejection): `state.run = { status: 'error', message: error.message }`.
5. `render()`.

**Results readout** (`resultsView.ts`) — deliberately plain, per this plan's scope-boundary resolution: one unstyled HTML `<table>`, one row per selected algorithm (labeled by `algorithm.name`), one column per headline metric — average wait, max wait, average travel, total distance, throughput, average occupancy %, deadhead %, unserved count/%, plus `trialCount` — read directly off `AlgorithmMetrics`. No charts, no color-coding, no sorting/highlighting "the winner," no per-run replay selector (that's Unit 07's `perTrial` consumer). An error state renders a plain `<p>` with the caught message instead of a table. This is enough to prove the whole pipeline actually ran and produced real numbers when clicked through in a browser, without building any part of Unit 07's dashboard.

### Validation (`validation.ts`)

Minimum viable, not a form-validation framework: the engine and generation layers already throw descriptive errors for the invalid configs that matter most (`doorDwellBaseMs <= 0` in `runSimulation`, negative `baseRatePerMinute`/`floorRates` in `generateRandomArrivals`) — Unit 06 does not re-implement those checks, it lets them surface via the `try/catch` in "Run controls" above and displays the thrown message as-is. `validate(state)` in this unit adds only the handful of checks needed to avoid a confusing failure mode the lower layers don't (and shouldn't have to) guard against:
- at least one algorithm selected (nothing throws for an empty algorithm list — `runTrialBatch` would just return `[]` and the results table would silently render empty, which is more confusing than a clear "select at least one algorithm" message),
- numeric fields parse to actual numbers (a blank/non-numeric `<input type="number">` yields `NaN` in the DOM, which would otherwise propagate into a `BuildingConfig` and fail deep inside the engine with a less legible message than catching it at the form boundary).

No per-field inline validation-as-you-type, no debouncing, no red-border/tooltip UI — a single guard function run once at "Run" time, and a single message shown if it fails.

**Correction (developer review, before implementation): floors must be constrained to a minimum of 1.** Traced what a `floorCount: 0` config actually does in Unit 04's random generator: under `up-peak`, `generateRandomArrivals` calls `uniformFloor(rng, 1, 0)` for a destination — `span = max - min + 1 = 0`, so it deterministically returns `1`, an out-of-bounds floor for a building whose only valid index is `0`. Under `random`, `uniformFloorExcluding(rng, 0, 0, 0)` has the identical bug (also returns `1`). Either would then reach `runSimulation`'s `handleTravel` bounds check and throw mid-run with a cryptic "out of bounds [0, 0]" message rather than a clear validation error at the form boundary. (`down-peak`'s `generatingFloors` is empty for `floorCount: 0`, so it happens not to crash — but a building with no floors above ground is a degenerate, uninteresting config for a multi-floor dispatch teaching tool regardless of pattern.) Fixed at the UI layer, not Unit 04: the "Floors (above ground)" input gets `min="1"` (HTML-level guard against the stepper/scroll-to-zero case) and `validate(state)` adds a matching explicit check, alongside the existing empty-algorithm-selection and NaN guards. This avoids touching an already-completed unit for what is, at bottom, a UI-input-range problem, consistent with this plan's existing "let lower layers throw; the UI only guards what would otherwise produce a confusing failure" philosophy.

### What gets tested

**Automated (Vitest, no DOM/jsdom)**: this is the first unit with real UI code, and the practical Vitest/DOM boundary is drawn here deliberately rather than overclaimed —
- `buildScenario.test.ts`: given a filled-out `ConfigDraft`, asserts the exact `Scenario` object produced, for both branches (`type: 'random'` including `floorRates` only for pattern-relevant floors with values actually entered; `type: 'scripted'` with the selected example's `building`/`script` passed through unchanged and the UI's trial count spliced in).
- `validation.test.ts`: exact pass/fail cases for the guards above (empty algorithm selection, `NaN` fields, `floorCount < 1`) — pure function, no DOM.

No jsdom dependency is added in this unit. `configPanel.ts`/`algorithmSelect.ts`/`runControls.ts`/`resultsView.ts`/`app.ts` — actual DOM construction, event wiring, and the focus-preserving `oninput` behavior described above — are **not** covered by Vitest here; they require either a DOM-simulation environment this project doesn't yet have, or a real browser, and the latter is what this plan uses.

**Manual/browser verification** (to be written up as `06_ui_test.md` during implementation, following this unit's `_test.md` template): run `npm run dev`, click through both scenario-type modes (build a random scenario with a per-floor override; load the `upPeakDemo` scripted scenario), toggle algorithm selection, click Run, and confirm the plain results table shows real, distinct-looking numbers per algorithm. Separately confirm at least once against `npm run build && npm run preview` — under the `/L-vator/` base path — since that's closer to what GitHub Pages will actually serve than the dev server is. Also manually trigger the error path (e.g. a scenario built with `doorDwellBaseMs` set to `0`) and confirm the caught message renders instead of a crash/blank page.

**Deviations from the plan, and why:**

- **`RunState` shape resolved to a fully consistent discriminated union.** The plan's own inline
  pseudocode in "State model" writes `'idle' | 'running' | {status:'done',...} |
  {status:'error',...}` (mixing bare string literals with objects), but the "Run controls"
  section's step 2 explicitly writes `state.run = { status: 'running' }` (an object). Implemented
  as `{status:'idle'} | {status:'running'} | {status:'done', metrics} | {status:'error',
  message}` throughout — one consistent shape discriminated on `status`, matching the "Run
  controls" section's own example and the project's established discriminated-union style (e.g.
  `PassengerRecord` in `src/metrics/types.ts`). Purely a type-shape clarification; no behavior
  described by the plan changes.
- **Floor-count structural re-render moved from `oninput` to `onchange`.** The plan lists "floor
  count changing" as a structural change requiring `render()`, but its own stated *reason* for
  the oninput/non-render split is "a full-subtree rebuild on every keystroke would destroy and
  recreate `<input>` elements, losing focus and cursor position while typing a number." Floors is
  itself a multi-digit number field, so triggering the structural `render()` on every keystroke
  (`oninput`) would reproduce exactly the focus-loss problem the plan is trying to avoid, just for
  this one field. Implemented instead with `oninput` mutating the value live (field stays
  responsive) but the structural `render()` firing only on `change` (blur/Enter — i.e. once the
  user has committed a value), which honors both the plan's "structural changes trigger render()"
  rule and its focus-preservation goal. Confirmed in browser testing: typing "8" into Floors does
  not lose focus, and the per-floor-rate panel correctly updates once the field is committed.
- **Scripted-example dropdown labeled positionally ("Example 1", "Example 2", …), not by
  filename/id.** The plan's "Scenario type toggle" section says examples are "labeled by
  filename/id since `ScriptedScenario` carries no display name field today" — but
  `src/scenarios/index.ts` (deliberately left unmodified by this unit, per its own explicit scope
  boundary) discards each module's filename when building its `scenarios: Scenario[]` export;
  only the `Scenario` objects themselves survive, with no filename/id attached. There is
  therefore no filename/id available to a consumer of that barrel without modifying
  `src/scenarios/index.ts`, which is out of this unit's scope. Labeled positionally instead
  (`Example 1`, `Example 2`, …) — the same "small gap, not worth a cross-unit change for one
  label" the plan itself already accepts, just resolved one layer more concretely once the actual
  export shape was checked.
- **`scenarios: Scenario[]` narrowed to `ScriptedScenario[]` at the UI layer.** `src/scenarios`'s
  exported type is the full `Scenario` union (nothing in its own types restricts it to scripted
  examples, even though every scenario file on disk today happens to export one) — assigning it
  directly to `ConfigDraft.scriptedScenario: ScriptedScenario | null` failed `tsc -b` type
  checking. Added a small `scriptedScenarios(): ScriptedScenario[]` filter (in `state.ts`, reused
  by `configPanel.ts`) rather than widening `ConfigDraft` to accept the full union — "Load example
  scenario" mode is specifically about scripted examples per the plan's own text, and this keeps
  `buildScenario`'s scripted branch simple and exactly-typed. `src/scenarios/index.ts` itself
  was not touched.

None of these change the plan's actual UI behavior, field set, defaults, validation rules, or the
Correction note's `floorCount >= 1` fix — they're type-shape/event-wiring/labeling resolutions
needed to make the plan's prose concrete against the real exported shapes of `src/scenarios` and
`src/generation`.
